# EasyGo 适老导航硬件开发

以当前仓库文件、器件资料、配置、源码、测试记录和用户确认内容为事实来源。把项目外资料视为候选依据，不把参考模块、旧项目设计或经验参数直接写成 EasyGo 的已定方案。

## 开始任务

1. 确认工作区为 `E:\Projects\EasyGo`。
2. 检查目录、版本控制状态和用户已有改动；若尚未初始化 Git，直接说明，不把它当作错误。
3. 完整读取与任务相关的文件，并读取 [references/project-state.md](references/project-state.md)。
4. 区分“已确认事实”“合理推断”“候选方案”“待验证事项”，为易变化结论附证据路径或测试记录。
5. 明确任务涉及产品、结构、硬件、固件、软件、定位、地图/POI、通信、照护端、隐私或测试中的哪些范围。
6. 修改跨域接口前，列出生产者、数据格式、消费者、失效行为和验证方法。

## 项目目录

- `0.References/`：器件资料、标准法规、竞品、论文、地图/POI 接口资料、参考代码和来源说明。
- `1.Model/`：外壳、按键、佩戴或携带结构、装配、工程图及必要导出件。
- `2.Hardware/`：原理图、PCB、BOM、天线、电池与充电、连接器、线束、接口和硬件测试资料。
- `3.Firmware/`：板级工程、驱动、定位、通信、低功耗、交互、状态机、围栏判断、升级与诊断代码。
- `4.Software/`：设备配置工具、照护端、移动端、服务端、厕所 POI 管理、地图导航、数据分析和自动化测试工具。
- `5.Docs/`：需求、架构、接口、隐私与安全、测试记录、决策记录以及本技能。

把新内容放入职责最接近的目录。只有形成明确模块后再增加子目录，不预先创建空的深层结构。

## 产品与需求

- 先定义目标用户、携带方式、使用环境、目标地区、主要照护关系和最小可用流程。
- 把“寻找厕所”“简单导航”“电子围栏”拆成可测试的用户任务，记录成功条件、超时、取消、误触和异常恢复。
- 为质量、尺寸、续航、充电、待机、定位时间、定位精度、导航更新率、提示方式、防护等级和成本设置带单位的指标；未确认时保持为待定。
- 优先降低认知负担：减少步骤和模式，使用大而明确的操作目标，提供清晰反馈，并避免仅靠颜色、细小文字或复杂菜单传达状态。
- 把“可到达厕所”“无障碍厕所”“开放时间”等属性与“距离最近”分开验证；数据源没有相应证据时不得承诺。
- 不把设备描述为医疗器械、生命保障或绝对防走失方案；明确定位、网络、地图和电量失效时的边界。

## 厕所搜索与简易导航

- 记录 POI 数据源、授权条件、覆盖地区、坐标系、更新时间、离线策略和字段可信度。
- 区分直线距离、道路距离、步行时间和实际可达性；输出中注明所用口径。
- 先确认当前位置的时间戳、精度和坐标系，再执行附近搜索或路线计算。
- 设计短而可恢复的提示：方向、距离、下一动作、偏航重算、到达确认和停止导航。
- 为室内、地下、楼群遮挡、弱网、无网、位置漂移、POI 关闭、路径受阻和地图过期设计降级行为。
- 不编造实时开放状态、无障碍设施或路线安全性；缺少数据时明确提示未知。

## 定位、电子围栏与告警

- 先确认定位来源及组合策略，例如 GNSS、蜂窝 LBS、Wi-Fi、BLE 或手机辅助；不要仅凭模块型号推断能力已接入。
- 定义围栏形状、坐标系、边界包含规则、采样周期、迟滞、连续判定次数、进入/离开事件、静默期和时钟要求。
- 同时评估漏报、误报、位置跳变、冷启动、跨围栏抖动、设备关机、无信号、低电量和时钟异常。
- 把“设备端判定”和“服务端判定”作为不同架构方案，记录网络依赖、功耗、延迟和隐私权衡。
- 为告警定义接收者、渠道、重试、去重、确认、升级和撤销流程；未经用户明确授权，不发送真实短信、电话、推送或位置数据。
- 不把单次定位点等同于真实越界；使用带精度、时间和连续性约束的判定策略，并通过实测确定参数。

## 结构与硬件

- 检查携带稳定性、跌落、误触、握持、按键力度、扬声器可听度、振动可感度、充电可达性、防水防尘、天线净空和维护空间。
- 以原理图、PCB、BOM、模块规格书和应用手册共同确认设计，不只依赖文件名、营销页或参考板截图。
- 检查电源树、峰值电流、蜂窝发射压降、充电与电池保护、热设计、ESD、接口电平、天线匹配和射频布局。
- 修改引脚、连接器、天线、传感器方向或电源时，同步检查固件、结构、测试和接口文档。
- 把 `0.References/` 中的 A7670 系列资料作为候选参考；在原理图、BOM 或用户决定出现前，不认定具体模块、制式、频段、认证或定位能力。

## 固件、软件与数据

- 先识别实际 MCU/SoC、RTOS、工具链、构建入口、目标板、启动流程、调试接口和升级方式。
- 处理 LVGL 页面、资源或 PC 仿真时，读取 [references/lvgl-simulator.md](references/lvgl-simulator.md)，保持固件页面源码与 Visual Studio 工程引用一致。
- 让关键状态可诊断：定位状态、网络状态、电量、时间同步、POI 数据版本、导航状态、围栏状态、告警状态和最近错误。
- 为设备与软件协议记录版本、字节序、单位、坐标系、时间基准、有效范围、超时、重试和兼容策略。
- 对低功耗策略同时验证唤醒延迟、定位可用性、告警时效、网络重连和实际续航。
- 原始测试数据保持只读；派生数据和报告分开保存，并附硬件版本、固件版本、配置、时间和实验条件。
- 对位置、轨迹、厕所请求、围栏和联系人数据执行最小化采集、明确同意、访问控制、传输与存储保护、保留期限和删除机制；把共享范围设计为可见、可撤销。

## 编译 ESP32 固件

1. 把工作目录设为 `3.Firmware/PlatformIO/EasyGo-ESP32-fw/`，先读取 `platformio.ini` 并确认目标环境仍为 `esp32dev`。涉及屏幕或触摸时，同时读取 [ESP32 Dev Module + ST7789 接线与点亮教程](../ESP32Dev-ST7789-Wiring-and-Bringup.md)。
2. 使用项目已安装的 PlatformIO 执行：

   ```powershell
   & 'C:\Users\24302\.platformio\penv\Scripts\platformio.exe' run
   ```

   若该绝对路径不可用，先查找当前环境中的 `platformio` 或 `pio`，不要擅自升级或重装工具链。
3. 以最终出现 `[SUCCESS]` 且命令退出码为 `0` 作为编译成功依据。主要产物为 `.pio/build/esp32dev/firmware.bin` 和 `.pio/build/esp32dev/firmware.elf`；仅执行 `run`，不要把编译任务扩大为烧录。
4. 编译失败时从日志中定位首个根因，避免被多个包含单元产生的重复错误干扰。修复后重新执行完整命令，直到链接、容量检查和固件镜像生成全部完成。
5. 遇到 `lv_font_montserrat_<字号> was not declared` 时，先用 `rg` 汇总 `src/` 中实际引用的字号，再在 `lib/lvgl/lv_conf.h` 中启用对应 `LV_FONT_MONTSERRAT_<字号>`。保留 UI 指定字号，不用相近字体掩盖配置缺失；同时检查 Flash 占用。
6. 中文 UI 使用 `font_easygo_12/14/16/20/28` 字形子集。修改中文文案后，检查字符是否包含在生成字体中；需要更新时运行 `4.Software/UI/tools/build_lvgl_assets.py`，并确认生成的 `.c` 文件仍参与固件构建。
7. 若 PlatformIO 在受限环境中无法写入用户目录下的 `platforms.lock` 或 `.cache`，把它识别为执行权限问题，并申请对现有 PlatformIO 用户目录的必要访问后重试；不要因此删除缓存或修改项目源码。
8. 只有在确认增量缓存陈旧时才执行 `platformio run --target clean`，随后重新运行正常构建。报告最终 RAM、Flash 使用率以及仍存在的警告；不要把警告描述为编译失败。
9. 当前首次点屏配置使用 ESP32 Dev Module + ST7789 240×320，并暂时关闭会产生引脚冲突的旧编码器、电源、外部数据 SD、IMU、蜂鸣器和蓝牙初始化；音频已改用独立引脚的 DFPlayer Mini。恢复其他外设前先完成新引脚分配，不得只把功能宏改回 `1`。
10. 电容触摸照片不能证明具体控制器型号。先读取串口 I²C 探测结果；只有检测到已支持的 FT6x36、CST816 或 GT911 才能宣称固件识别，屏幕显示成功不等于触摸已验证。
11. DFPlayer Mini 使用 GPIO17/26 的 UART2 和自身 microSD 音频卡；涉及接线、文件编号或串口排查时读取 [DFPlayer Mini + microSD 音频教程](../DFPlayer-Mini-SD-Audio-Bringup.md)。不要把 DFPlayer 卡描述成 ESP32 可挂载的 `S:/` 数据卡。

## LVGL 页面与模拟 SD 数据

- 把 `3.Firmware/PlatformIO/EasyGo-ESP32-fw/src/App/` 作为页面、账户、组件和资源代码的唯一来源；让 Windows 模拟器直接引用这些文件，不复制第二套页面源码，不恢复旧 `Peak-ESP32-fw` 路径。
- 保留现有 `Page / View / Model / ResourcePool` 架构。新增、删除或重命名页面和资源时，同步更新页面注册、工厂匹配、跳转路径、资源池、`.vcxproj` 与 `.vcxproj.filters`。
- 统一按 SD 卡根目录组织数据：PC 宿主目录使用 `4.Software/Simulator/SD/`，PC LVGL 路径使用 `/SD/...`；实体卡根目录不包含 `SD` 这一层，固件通过 `S:/...` 读取。把路径差异集中在 Model 或平台适配层，不散落在 View 中。
- 把地图显示资源与可查询数据分离。`MAP/shenzhen.bin` 是 RGB565 栅格图，只用于显示，不能直接查询厕所；附近厕所查询必须读取独立 POI 索引，并记录 POI 标识、名称、经纬度、属性、坐标系、来源、数据日期和许可。
- 不对 SD 文件源的 RGB565 图片直接调用 `lv_img_set_zoom()`；LVGL 对文件源逐行解码，而图片变换需要完整像素缓冲。优先生成相同画布尺寸的多级地图文件并切换路径，只有确认连续内存预算后才改为整图加载。
- 地图拖动采用“240×164 可滚动视口 + 720×492 内容画布”：底图、路线、当前位置和目标放入同一个内容层，缩放按钮与固定说明放在根层；禁用滚动链和弹性越界，避免拖动地图触发页面切换或露出空白。
- 真机触摸拖动依赖已注册并校准的 `LV_INDEV_TYPE_POINTER` 输入设备。PC 鼠标拖动通过只证明 LVGL 页面逻辑成立；若固件仍只有编码器输入，必须在确定触摸控制器、引脚和坐标方向后补充触摸驱动。
- 为每个地图层级保存 WGS84 边界、像素尺寸、内容边距和米/像素，并使用 64 位中间值完成经纬度到像素的投影。导航时围绕最新有效定位点选择地图窗口，不把固定行政区中心当作真实当前位置。
- 不把地图上画出的厕所图标等同于已实现查询算法。使用当前 OSM 快照生成并校验 `shenzhen_toilets.bin` 后，再验证附近筛选、距离口径、排序、无结果、过期数据和坐标转换。
- 从 `CONTACTS/contacts.csv` 动态加载联系人，格式保持为 `姓名,脱敏号码,头像样式编号`。在 Model 中完成有界读取、字段校验、空行和 `#` 注释处理及缺失/空文件回退；当前上限为 16 条。
- 让联系人卡片在独立容器内动态创建并纵向滚动，保持顶部标题和底部 SOS 固定。样例仅使用合成或脱敏数据，点击演示不得触发真实拨号、消息或位置发送。
- 修改中文字体或地图资源时复用 `4.Software/UI/tools/build_lvgl_assets.py`。生成字体时让 `getbbox(anchor="ls")` 与 `draw.text(..., anchor="ls")` 使用相同基线锚点，并同步注册生成源文件。
- 修改完成后同时验证 XML 工程项、`Debug|x64` 构建、程序启动、SD 文件成功与失败分支、页面视觉、页面跳转和列表实际滚动；不得用“进程存活”代替交互验收。

## 安全与授权

- 按任务需要执行构建、静态检查、单元测试和不接触真实用户数据的仿真。
- 只有用户明确要求后，才执行烧录、复位、连接真实蜂窝网络、写入 SIM/密钥、触发真实告警、上传真实位置或改变硬件供电。
- 硬件动作前说明固件来源、目标板、供电与限流、连接方式、可能费用、停止方法和预期现象。
- 首次上电从限流电源和最小外设开始；出现异常电流、过热、异味、电池鼓胀、反复复位或射频异常时立即停止。
- 使用合成或脱敏位置做开发测试；不得把真实老人轨迹、联系人或家庭地址写入源码、日志、样例或提交记录。
- 涉及老人安全时，优先验证失效提示、人工求助路径和恢复能力，不以实验室单次成功代替实际场景可靠性。

## 验证与交付

- 执行与风险相称的检查，优先使用仓库已有构建预设、测试脚本和配置。
- 分层验证：纯逻辑测试、仿真/回放、台架测试、受控场地测试、真实目标环境试用；不得把其中一种写成另一种。
- 至少覆盖正常、边界和失效场景，并记录预期结果、实际结果、版本、时间、环境和原始证据。
- 报告实际执行的命令与结果；把未运行的硬件、网络、户外或真实用户验证明确标为未运行。
- 最终用中文说明结论、依据、修改文件、验证结果、尚未确认事项、风险和建议下一步。
- 只有用户明确要求提交或推送时才执行 Git 操作；禁止强制推送。

## 随项目进度维护本技能

每次完成阶段性需求、选型、接口变更或可复现实验后，检查并更新：

1. 把仓库文件、用户决定或实验确认的当前事实写入 [references/project-state.md](references/project-state.md)，注明证据与日期。
2. 把稳定且会重复使用的工作流程写入本 `SKILL.md`。
3. 把详细协议、数据格式、隐私规则或专项调试方法放入 `references/` 下的独立文件，并从本文件直接链接。
4. 用新证据替换过时的当前事实；把历史过程留在版本记录、决策记录或测试报告中。
5. 在目录、工具链、硬件、定位方案、POI 数据源、围栏算法、通信协议、安全边界或验证流程变化时，同步检查本技能。
6. 更新后运行 `skill-creator` 的 `quick_validate.py`，并确认 `agents/openai.yaml` 与技能名称和用途一致。
